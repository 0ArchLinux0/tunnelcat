## Critical thinking on the gate

The friend test (M1.17) is the only M1 sub-step that matters.
The user-side acceptance criterion is:

> A friend you've never met can run `curl ... | sh` and `tunnelcat
> dial <token>` and have a working tunnel in under 10 minutes.

What the code can verify (and did): every local test green, CI
green on darwin/amd64, darwin/arm64, linux/amd64, README is
self-contained, install.sh works on the host. What the code
CANNOT verify: that a real human, on a different network, with
a different OS, with a corporate firewall, can follow the
README and end-to-end run the flow.

That's a human test. Per your standing rule, the agent does not
run the friend test. The user does, when ready.

## What worked

- The withLockedFile/saveLocked pattern (saving once, refactoring
  out the no-lock inner version) is now applied identically in
  identity and contacts. Same code shape, same locking semantics.
  The M0 closure doc called this out as the right pattern; M1
  made it concrete.
- Splitting subcommands into per-file (M1.2) made the next 12
  sub-steps cheap. Each new verb is a new file + an `init()`.
- The CI cross-build job (M1.13) caught a real failure mode: the
  `go` job had been failing on cgo because the Rust crate wasn't
  built. The fix (build rust inside the go job) is one sentence;
  the diagnostic took longer than the fix.
- The user's "go on til finished" instruction kept the agent from
  stopping at every sub-step boundary for a check-in.

## What didn't

- The deadlock in `withLockedFile` calling `Save` (which also
  locks) was caught by the contacts test suite, not by CI. CI
  only re-runs the existing test suite; it doesn't re-run a test
  that just landed. Lesson: any race-condition test that needs
  `-race` or `-count=N` to expose the bug should be invoked in
  the same PR as the fix.
- `gofmt` (Go 1.27) is stricter about comment indentation than
  Go 1.22. Six files had to be re-formatted after the env
  changed. The `gofmt` step in CI catches this now, so the next
  release won't repeat it.
- `tailcat.ConnBlob` is a string type, not a struct. "Build a
  ConnBlob from a pubkey" isn't a one-call operation; the
  friend has to actually send the token. M1.8 therefore
  evolved into: lookup-by-name, but only after the user has
  stored the token via `contact set-blob <name> <token>`.
  Acceptable for M1; the "scan QR, get a name" UX is M1.10's
  territory, and the QR code (printed on the server side) is
  the friend→user channel for the token.

## What to verify before declaring M1 done

1. Pick a friend. They have never seen this code.
2. Send them the install one-liner.
3. You run `tunnelcat up --identity=home` and read them the
   `tc...` token (or send a screenshot of the QR code).
4. They run `tunnelcat contact add home <your pubkey>` and
   `tunnelcat contact set-blob home <token>`.
5. They run `tunnelcat dial home --port 12345`. You both see
   echoed input.
6. If step 5 fails, run `tunnelcat doctor` on both sides.
7. If the friend is stuck, write down *what they tried* and
   *what they expected* — that's the M2 spec, not a bug.

When the friend succeeds, M1 is done. The next milestone
(M2) is the Rust type-state Meow.

## Carried into M2 (not forgotten)

- `tunnelcat up` default identity is ephemeral. M2 should
  default to the named identity `--identity=default` if it
  exists. (No user-visible bug, but a friction point.)
- `tunnelcat doctor` check #4 (UDP outbound) is best-effort.
  It always says ✓. M2 should add a real STUN-style check.
- The release workflow (M1.14) is set up but not yet exercised
  end-to-end. The first `v0.2.0` tag will be the first real
  test.
- M1.9 (--allow) does not yet auto-populate from contacts. The
  user has to type `--allow=alice` on every `up`. M2 should
  default to "allow everyone in contacts" if any contact has
  a ConnBlob set.
