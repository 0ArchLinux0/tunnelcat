# M1 plan — "I can give this to one friend"

> **Date:** 2026-08-30
> **Status:** planning, not yet started
> **Roadmap:** [ROADMAP.md §M1](../ROADMAP.md#m1--i-can-give-this-to-one-friend-target-12-weeks)
> **Closure doc (when done):** `canon/closures/M1-<date>.md` (≤4 KB)
> **Sub-step count target:** 15–20 (vs the 8 in the M0 closure doc).
> Each sub-step is one branch + one commit + one verify command
> + one unit/integration test.

## Why this plan is bigger than the M1 sub-stepping in the M0 closure

The M0 closure doc had 8 sub-steps. That was a *summary*, not
a working plan. This document is the working plan: each
sub-step is a single thing you can implement, test, and merge
in one sitting (1–3 hours). If a sub-step takes longer than
that, it's too big and should be split.

The 8 in the closure doc become ~15 here, with the difference
being: every implementation sub-step now has a paired
*verification* sub-step (a unit test) and a paired
*documentation* sub-step (a docs update or a usage example).

## Critical-thinking commentary on the M1 gate

The M1 gate (in ROADMAP.md) is:
> A friend can run a one-liner on their Mac or Linux machine
> and connect to your tunnel. They don't need a GitHub
> account, a Tailscale account, or a config file. They need
> a token. The token can be a string, a QR code, or a
> DNS TXT record.

**Critique 1 (gate is well-scoped).** The "friend" test is a
real acceptance criterion: it's a person who has never seen
the project, with no prior context, running a one-liner. If
the friend can do it, M1 is done. This is the right shape of
gate — measurable, user-facing, low-ceremony.

**Critique 2 (gate has hidden assumptions).** "They need a
token" assumes the user can get the token to the friend. We
list "a string, a QR code, or a DNS TXT record" but the gate
doesn't say *which* of these the user must do. The plan must
pick at least one (string is the easiest; QR is the
"delightful" option; DNS is the "I'm a power user" option).
**Decision: string is the M1 floor, QR is the M1 nice-to-have,
DNS is M1+1 (M1.5 or M2).**

**Critique 3 (the README is underspecified).** "A README with
a 5-minute quickstart" is a content requirement, but it
doesn't say *what* the quickstart covers. A friend needs to
know: how to install, how to get a token from me, how to run
the server, how to run the dial, how to clean up. That's 5
sections; each is a sub-step.

**Critique 4 (CI is good but unclear).** "CI green on a real
GitHub repo" is a checkbox, but the .github/workflows/test.yml
we wrote in M0 is already there and runs. The M1 CI work is
about (a) adding the cross-build step, (b) adding the
identity/contact tests, (c) the release workflow. Three
things, not one.

**Critique 5 (the install script is not in the gate but should
be).** The M0 install.sh works but it's release-scoped
(downloads from GitHub Releases). M1 needs a `tunnelcat
install` or similar that the friend can run on their own
machine — different scope from the release install. We can
either (a) reuse the release install, (b) write a
`dev-install` that compiles from source. **Decision: (a) is
fine; friends install from the release page, not from
source.**

## The 17 sub-steps (numbered for grep, M1.1 ... M1.17)

Each sub-step ends with:
- **Verify:** the one-line shell command that proves it's done
- **Test:** the unit/integration test that exercises the behavior
- **Commit:** the commit message (so `git log --oneline` shows the trail)
- **Critical:** the critical-thinking commentary (why this might fail, what's risky, what to watch for)

### M1.1 — Add `install.sh` to the repository

**What:** Move `install.sh` (currently generated by `bin/release.sh` into `dist/`) into a top-level `install.sh` that lives in the repo. This way, `curl https://raw.githubusercontent.com/.../install.sh | sh` works for HEAD (not just releases).

**Why first:** every subsequent sub-step that ships code can be tested by "rebuild and re-run install.sh on a fresh Mac" — and the friend test is the M1 gate, so install needs to be solid.

- **Verify:** `curl -fsSL file://$PWD/install.sh | bash` (or `sh install.sh` directly with no install dir arg) puts tunnelcat on PATH.
- **Test:** install on a clean Mac VM (or a Docker `ubuntu:latest` container if you don't have a Mac VM handy).
- **Commit:** `feat(install): top-level install.sh works for HEAD, not just releases`
- **Critical:** the current `install.sh` only knows about release tarballs. The HEAD version needs to know how to build from source. Decide: does install.sh detect "we have go installed" and run `go install`? Or always download a tarball? For M1, "always download a tarball" is simpler. **Defer "go install from source" to M5 (polish).**

### M1.2 — Refactor `cmd/tunnelcat/main.go` for subcommands

**What:** The current `main.go` has `runUp()` and `runDial()` inline. Refactor each into its own file (`up.go`, `dial.go`) so adding new subcommands (identity, contact, etc.) doesn't bloat `main.go`. The `run()` dispatch in `main.go` becomes a switch over registered subcommands.

**Why second:** every new sub-step in M1 adds a new file. Without this refactor, `main.go` would grow to 1000+ lines by M3.

- **Verify:** `wc -l cmd/tunnelcat/main.go` is under 100 (it's currently 200+).
- **Test:** all existing unit tests still pass.
- **Commit:** `refactor(tunnelcat): split up.go and dial.go out of main.go`
- **Critical:** the test file `main_test.go` depends on the `run()` function being accessible. The refactor must keep `run()` exported (lowercase, but package-accessible) so tests still work.

---

### M1.3 — Add `internal/identity` package skeleton

**What:** Create `internal/identity/identity.go` with three exported functions: `Load() (*Identity, error)`, `Save(*Identity) error`, `New() (*Identity, error)`. The `Identity` struct holds a `key.NodePrivate` and metadata (name, created-at). The package owns the `~/.config/tunnelcat/keys/default.private.json` file format.

**Why third:** every later sub-step (init, show, add, dial-by-name) uses this package. Get the file format right here, get the load/save right here, before adding CLI on top.

- **Verify:** `go build ./internal/identity/` succeeds. A unit test creates a temp dir, calls `Save`, then `Load`, and asserts round-trip.
- **Test:** `internal/identity/identity_test.go` with `TestLoadSaveRoundTrip`, `TestLoadMissingFile`, `TestLoadCorruptFile`.
- **Commit:** `feat(identity): package skeleton with Load/Save/New`
- **Critical:** the file format must be forward-compatible (new fields can be added without breaking old files). Use a `version: 1` field at the top of the JSON. Also: the file contains a Curve25519 private key; it must be `chmod 0600` on save. **Watch for: forgetting the chmod.**

### M1.4 — Implement `tunnelcat identity init`

**What:** A new subcommand that calls `identity.New()`, prompts (or uses a `--name` flag) for the device name, and saves to `~/.config/tunnelcat/keys/<name>.private.json`. If `--name` is not given, default to `default`.

**Why fourth:** this is the user's first action on a new device. It needs to be simple, fast, and idempotent (running it twice with the same name is OK; running it twice with a different name is a recoverable error).

- **Verify:** `tunnelcat identity init --name=studio-mac` creates the file, prints the public key, exits 0. `tunnelcat identity init --name=studio-mac` a second time says "key already exists, use --force" and exits 1.
- **Test:** `cmd/tunnelcat/identity_test.go` with `TestIdentityInit` (uses a temp HOME) and `TestIdentityInitAlreadyExists`.
- **Commit:** `feat(identity): tunnelcat identity init`
- **Critical:** the CLI must NOT call `os.Exit` directly; it must return an int from `run()`. This is a testability constraint. Also: on macOS, the home dir is `~/Library/Application Support/tunnelcat/` (XDG-lite), not `~/.config/`. **Decide: do we use XDG_CONFIG_HOME everywhere, or do we use platform-specific paths?** XDG everywhere is simpler; let me default to that. Watch for: `os.UserHomeDir()` returning something unexpected in CI.

---

### M1.5 — Implement `tunnelcat identity show`

**What:** Reads the identity file (default or `--name=<n>`), prints the public key in the same format tailcat uses: `nodekey:<hex>`.

**Why fifth:** the user (or the friend) needs to give the public key to the other side. Without `show`, the user has to grep the JSON file.

- **Verify:** `tunnelcat identity show` prints `nodekey:abc...` and exits 0. `tunnelcat identity show --name=nonexistent` exits 2 with "no such identity".
- **Test:** `cmd/tunnelcat/identity_test.go` with `TestIdentityShow`.
- **Commit:** `feat(identity): tunnelcat identity show`
- **Critical:** the public key is 32 bytes hex. Print it lowercase, no `0x` prefix, no spaces. Match `tailcat`'s format exactly so the friend can paste it into a `tailcat` config and it just works.

### M1.6 — Add `internal/contacts` package skeleton

**What:** A YAML file at `~/.config/tunnelcat/contacts.yaml` with this structure:
```yaml
version: 1
contacts:
  - name: studio-mac
    pubkey: nodekey:abc...
    last_seen: 2026-08-30T15:00:00Z    # optional, updated when we dial them
    last_addr: "100.64.0.2:22"          # optional, populated on dial
  - name: home-server
    pubkey: nodekey:def...
```

The `internal/contacts/contacts.go` exposes: `Load() (File, error)`, `Save(File) error`, `Add(File, Contact) (File, error)`, `Find(File, name) (Contact, bool)`, `List(File) []Contact`.

**Why sixth:** the dial-by-name feature (M1.8) depends on this. The contact list is the user's mental model of "the devices I trust." It needs to be human-editable (YAML) and machine-readable (the package).

- **Verify:** a unit test creates a temp contacts file, calls `Add`, `Save`, reloads with `Load`, asserts the contact is there. Another test calls `Find` with a missing name and gets `(Contact{}, false)`.
- **Test:** `internal/contacts/contacts_test.go`.
- **Commit:** `feat(contacts): package skeleton with Load/Save/Add/Find/List`
- **Critical:** YAML is the right format for humans but Go's `gopkg.in/yaml.v3` adds a dependency. We currently have zero non-tailscale.com deps. **Watch for: dependency creep.** Decide: do we accept the YAML dep, or do we use a simple key=value format? For M1, accept the YAML dep (one new module, that's all).

---

### M1.7 — Implement `tunnelcat contact add/list/remove`

**What:** Three subcommands that wrap the contacts package.
- `tunnelcat contact add <name> <pubkey>` — adds to contacts.yaml
- `tunnelcat contact list` — prints all contacts as a table
- `tunnelcat contact remove <name>` — deletes from contacts.yaml

**Why seventh:** these are the user's tools for managing the contact list. The friend test (M1 gate) doesn't strictly need `add` (the user can edit YAML by hand), but the friend test is smoother with it.

- **Verify:** `tunnelcat contact add studio-mac nodekey:abc` succeeds, `contact list` shows it, `contact remove studio-mac` deletes it, `contact list` is empty.
- **Test:** `cmd/tunnelcat/contact_test.go` with `TestContactAddListRemove`.
- **Commit:** `feat(contacts): tunnelcat contact add/list/remove`
- **Critical:** the pubkey arg should be validated as a valid `nodekey:` hex string, not just "any string." **Watch for: silent acceptance of malformed pubkeys.** The validation regex is `^nodekey:[0-9a-f]{64}$`.

---

### M1.8 — Implement `tunnelcat dial <name>` (lookup by contact)

**What:** Extend the existing `tunnelcat dial` to accept a contact name as the first arg, not just a raw `tcom...` token. If the arg starts with `tcom`, treat as token (M0 behavior). Otherwise, look up the contact by name and use their pubkey to construct a ConnBlob.

**Why eighth:** the friend test. Without this, the user has to copy a long token. With this, the user types `tunnelcat dial studio-mac --port 22`.

- **Verify:** `tunnelcat dial nonexistent` exits 2 with "no such contact." `tunnelcat dial studio-mac --port 22` dials the contact. (The e2e test from M0 should still work with a token arg.)
- **Test:** `cmd/tunnelcat/e2e_test.go` extended with a contact-based variant of the round-trip.
- **Commit:** `feat(dial): tunnelcat dial accepts contact names`
- **Critical:** the contact-to-ConnBlob conversion is non-trivial. A `ConnBlob` contains the server's pubkey + DERP region info. The contact list has the pubkey, but not the DERP region. We need to fetch the DERP map and pick the nearest region. **Watch for: silent default to derp-0 when DERP map fails.** Use the same logic `tailcat.Server.Start()` uses for picking a region.

---

### M1.9 — Implement `--allow` enforcement on the server

**What:** When the server has an identity (a `tunnelcat up --identity=<name>` flag), it only accepts connections from clients whose public key is in the server's allowlist. The allowlist is derived from the user's `contacts.yaml` (anyone you trust).

**Why ninth:** without this, anyone with the token can connect. With this, the token (which is just an address) is useless without also being on the contact list. This is the first real security feature.

- **Verify:** start a server with `--identity=studio-mac`. Start a client with a pubkey NOT in the contacts file. The server should reject the Meow packet. Start a client with a pubkey IN the contacts file. The server should accept.
- **Test:** `cmd/tunnelcat/allowlist_test.go` with `TestAllowlistRejectsUnknown`, `TestAllowlistAcceptsKnown`.
- **Commit:** `feat(security): --allow enforcement on the server`
- **Critical:** the server's allowlist is the SAME as the user's contacts (one-way trust, not mutual). The server trusts anyone the user has added to their contacts, regardless of whether the contact has reciprocated. **Watch for: confusing the user about "who trusts whom."** Add a `tunnelcat status --explain` in M3 to clarify.

### M1.10 — Implement `tunnelcat show --qr`

**What:** A new subcommand that prints the device's connection token as a QR code to the terminal. The friend can scan the QR with their phone or laptop webcam to capture the token without copy-paste.

**Why tenth:** the "delightful" option. Not strictly required for M1, but mentioned in the gate. Without it, the gate is met (string token works); with it, the gate is exceeded.

- **Verify:** `tunnelcat show --qr` prints a scannable QR code to stdout. Manual: scan with a phone, get the token.
- **Test:** `cmd/tunnelcat/qr_test.go` with `TestShowQR` (asserts the output contains QR code control characters from a known library).
- **Commit:** `feat(qr): tunnelcat show --qr`
- **Critical:** QR code libraries for Go terminal output: `github.com/mdp/qrterminal` is the de-facto choice. **Watch for: terminal width.** The QR code is fixed size; in narrow terminals, it wraps. The flag `--qr-size=small|medium|large` lets the user pick.

### M1.11 — Add `internal/installpath` for XDG-aware config paths

**What:** A tiny package with one function, `ConfigDir() (string, error)`, that returns the right config dir for the current OS:
- macOS, Linux: `$XDG_CONFIG_HOME/tunnelcat` (default `~/.config/tunnelcat`)
- Windows: `%AppData%/tunnelcat`

**Why eleventh:** every subsequent package (identity, contacts) needs this. Get it right once, reuse everywhere.

- **Verify:** with `XDG_CONFIG_HOME=/tmp/xdg`, `ConfigDir()` returns `/tmp/xdg/tunnelcat`. With `XDG_CONFIG_HOME` unset on Linux, it returns `~/.config/tunnelcat`.
- **Test:** `internal/installpath/installpath_test.go` with `TestConfigDirXDGOverride`, `TestConfigDirDefault`.
- **Commit:** `feat(config): XDG-aware config dir helper`
- **Critical:** on macOS, the Apple-recommended path is `~/Library/Application Support/`. We chose XDG everywhere for simplicity. **Watch for: a user filing an issue saying "why doesn't this follow the macOS convention?"** Defer to M5 (polish) if it comes up.

### M1.12 — README with 5-minute quickstart

**What:** A `README.md` with 5 sections, each answering one question. The current README is upstream's. Replace it.

1. **What is tunnelcat?** (3 sentences, no jargon)
2. **Install** (`curl ... | sh`, 1 line)
3. **First connection** (server on A, dial on B, full example)
4. **Manage identities and contacts** (`identity init`, `contact add`, etc.)
5. **Troubleshooting** (top 3 things that can go wrong: DERP not reachable, port conflict, contact not found)

**Why twelfth:** the M1 gate explicitly requires this.

- **Verify:** a non-author can follow the README end-to-end and successfully form a tunnel. (The "friend test" is this.)
- **Test:** manual, not automated. The agent is not the user. Have a friend (or a stranger from a Discord server) try it.
- **Commit:** `docs: README with 5-minute quickstart`
- **Critical:** the README must NOT use words like "NAT traversal," "WireGuard," "DERP," "magicsock" in the first 3 sections. **These are jargon that a friend doesn't know.** Use the friend test: would my mom understand the first 3 sections? If not, rewrite.

### M1.13 — CI: add cross-build step to `.github/workflows/test.yml`

**What:** A new job in the workflow that builds the 5 platform binaries (the same set `bin/release.sh` builds) and uploads them as workflow artifacts. This is the per-PR check that the cross-build is healthy.

**Why thirteenth:** without this, the cross-build can silently break and we only find out at release time.

- **Verify:** push a branch, the CI runs the cross-build job, all 5 platforms produce a binary, the workflow's green check appears.
- **Test:** a deliberate break (e.g., a Go file that only compiles on darwin) should make the cross-build job fail.
- **Commit:** `ci: add cross-build job to test workflow`
- **Critical:** GitHub Actions runners have limited disk (14 GB on Linux, smaller on macOS). **The cross-build may OOM on the macOS runner.** Watch for: job fails with "out of disk." If it does, the fix is to build the Rust crate in `release` mode (smaller output) and to use `actions/cache` for the Go build cache.

### M1.14 — CI: add release workflow that runs on tag

**What:** A `.github/workflows/release.yml` that triggers on a `v*` tag push, runs the test suite, runs `bin/release.sh v$TAG`, and uses `softprops/action-gh-release` to create the GitHub Release with the 5 tarballs attached.

**Why fourteenth:** this turns "cut a release" from a 30-minute manual process into a 1-minute `git tag v0.2.0 && git push --tags`.

- **Verify:** push a tag like `v0.2.0-rc1`, the release workflow runs, the GitHub Release is created with the 5 tarballs, the install.sh works.
- **Test:** manual (releases are expensive to test).
- **Commit:** `ci: release workflow on tag push`
- **Critical:** the GitHub Actions `GITHUB_TOKEN` has `contents: write` permission by default for tag-triggered workflows, but **for some org settings, you may need to add `permissions: contents: write` explicitly to the workflow.** Watch for: release workflow runs, all the way through, but the release is never created — that's a permissions issue.

---

### M1.15 — Add a `--log-level` flag to the data plane

**What:** The current `tailcat.Server` and `tailcat.Client` write a LOT to stderr (WireGuard handshake details, magicsock endpoint discovery, etc.). The M0 `tunnelcat --version` already does it; `tunnelcat up` does it; everything does it. The friend test (M1) will be buried in noise.

The fix: a `--log-level` flag that takes `info|warn|error` (default `warn`) and passes it to `tailcat.Server.Logf` and `tailcat.Client.Logf` via the `logger.Logf` interface.

**Why fifteenth:** the friend test is the M1 gate. A friend who sees 200 lines of WireGuard handshake noise will be confused. The M0 logs are useful for debugging; the M1 default should be quiet.

- **Verify:** `tunnelcat up` (default) writes 5 lines to stderr. `tunnelcat up --log-level=info` writes 200. `tunnelcat up --log-level=error` writes 0.
- **Test:** `cmd/tunnelcat/log_test.go` with `TestLogLevelDefault`, `TestLogLevelInfo`, `TestLogLevelError`.
- **Commit:** `feat(log): --log-level flag for the data plane`
- **Critical:** the `logger.Logf` interface is `func(format string, args ...any)`. The default `log.Printf` is fine; for "quiet," we use `logger.Discard` (which is `func(...) {}`). **Watch for: setting `Logf = logger.Discard` while still using `log.Printf` in our own code.** Our own logging should go through a separate logger.

### M1.16 — Add `tunnelcat doctor`

**What:** A new subcommand that runs 5 diagnostic checks and prints a report:
1. Can the binary reach `derp.tailscale.com` (or `--derp=<host>`)? (TCP dial + DERP handshake)
2. Is the local identity file present and valid?
3. Is the contacts file present and parseable?
4. Is the public key in any contact's allowlist? (Or: "you have N contacts, but no one trusts you yet" — that's a hint for the user)
5. Is the local firewall blocking outbound UDP? (Best-effort: try to dial a known UDP port)

**Why sixteenth:** the friend test will fail in some way we can't predict. `tunnelcat doctor` is the user's first line of defense. Without it, they come to us for help; with it, they self-diagnose.

- **Verify:** `tunnelcat doctor` prints 5 lines, one per check, each prefixed with `✓` or `✗`. The `✗` checks have a one-line suggestion ("try: tunnelcat up --log-level=info").
- **Test:** `cmd/tunnelcat/doctor_test.go` with `TestDoctorAllGreen` (uses a stub server) and `TestDoctorOneRed` (kills the DERP check).
- **Commit:** `feat(doctor): tunnelcat doctor diagnostic subcommand`
- **Critical:** the DERP check should NOT block for more than 5 seconds. Use a context with a 5-second timeout. **Watch for: the doctor hanging on a slow network.**

### M1.17 — Friend test: the M1 gate, end-to-end

**What:** A friend (a real human who has never seen tunnelcat) runs the install one-liner, follows the README, and forms a tunnel with the user. The user does NOT help beyond the README. The friend succeeds in under 10 minutes. The user records the friend's reaction and any "I wish this had said X" feedback.

**Why seventeenth (last):** the gate. Nothing else matters if the friend can't do it.

- **Verify:** the friend runs `tunnelcat up` and the user runs `tunnelcat dial <token>`, and they see the echo. Total time from install to working tunnel: under 10 minutes.
- **Test:** manual. This is the M1 acceptance test.
- **Commit:** no commit (this is the gate, not code). M1 is done; write the M1 closure doc and move to M2.
- **Critical:** the friend must be a real human, not the agent role-playing as a friend. **The agent cannot test the gate.** Pick a friend, send them the install command, watch.

## Risks specific to M1 (the gate, not the sub-steps)

- **The friend has a corporate laptop with strict egress rules.** The DERP relay (port 443) might be blocked. **Mitigation:** M1.10's QR code + DNS TXT record is the fallback; the friend gets the token another way. We need at least one alternate path documented.

- **The friend has an M1 Mac (Apple Silicon) but the only release tarball is amd64.** The install script detects arch; it works. **Mitigation:** the cross-build job (M1.13) tests this every PR.

- **The friend has never used the command line.** The README has to be clear to this person. **Mitigation:** the "5 sections" structure of the README (M1.12) is designed for the never-used-CLI friend. We may iterate on the README after the first friend test.

- **The friend doesn't trust the install one-liner.** This is a real concern; many people have been taught to never `curl | sh`. **Mitigation:** the README shows the install command AND a 2-line manual alternative (download tarball, extract, add to PATH).
