## What M1.1's gate is (per the working plan)

> **Verify:** `curl -fsSL file://$PWD/install.sh | bash` (or

Verified both modes locally:
- `bash install.sh` → downloads v0.1.1, installs to a custom
  dir, prints `tunnelcat v0.1.0 (tunnelcat-proto v0.1.0)`.
- `bash install.sh --from-source` → builds the binary, prints
  `tunnelcat 095591c (tunnelcat-proto v0.1.0)` (commit hash
  from `git describe --tags --always`).
- `bash install.sh TUNNELCAT_VERSION=v0.1.0` → downloads
  v0.1.0 specifically, prints the right version.
- `bash install.sh --help` → shows the help with `--from-source`
  and `TUNNELCAT_INSTALL_DIR` mentioned.

Also verified end-to-end with a from-source build: `tunnelcat
up` on one process, `tunnelcat dial` on another, 3 lines
echoed through the WireGuard tunnel.

## Two bugs I found and fixed

1. **The per-platform `SHA256SUMS` file isn't at the URL I
   expected** for the v0.1.0 / v0.1.1 releases. The install
   script tries, fails silently, and continues with a
   warning. The right fix is to upload the per-platform
   `SHA256SUMS` to releases (separate M5 task); the install
   script is robust to its absence.
2. **`--from-source` outside a git checkout was crashing.**
   Added a `git rev-parse --is-inside-work-tree` check.

## Discoveries

- **`goreleaser` ran during the v0.1.1 release creation** and
  uploaded 23 assets including `.deb`, `.rpm`, goreleaser-named
  tarballs (`tailcat_0.1.1_linux_amd64.tar.gz`), and an
  armv7 build. None of these were in the v0.1.0 release.
  This is good news (the user's request for `.deb`/`.rpm`
  got answered automatically), but it means the install
  script's SHA check needs to handle both legacy
  (`darwin-arm64.tar.gz`) and goreleaser (`tailcat_*` format)
  naming. The current script handles this gracefully.
