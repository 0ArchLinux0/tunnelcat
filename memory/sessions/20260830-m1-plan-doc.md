## What the doc contains (the structure)

Each of the 17 sub-steps has:
- **What** — the change to make
- **Why** — why this sub-step, in dependency order
- **Verify** — the one-line shell command that proves the sub-step is done
- **Test** — the unit/integration test that exercises the behavior
- **Commit** — the commit message (so `git log --oneline` shows the trail)
- **Critical** — critical-thinking commentary: what could fail, what's risky, what to watch for

The 17 sub-steps are:
1. `install.sh` in repo (not just in `dist/`)
2. Refactor `main.go` (split `up.go` and `dial.go` out)
3. `internal/identity` package skeleton
4. `tunnelcat identity init`
5. `tunnelcat identity show`
6. `internal/contacts` package skeleton
7. `tunnelcat contact add/list/remove`
8. `tunnelcat dial <name>` (lookup by contact)
9. `--allow` enforcement on the server
10. `tunnelcat show --qr`
11. XDG-aware config dir helper
12. README 5-minute quickstart
13. CI cross-build job
14. CI release workflow
15. `--log-level` flag for the data plane
16. `tunnelcat doctor` diagnostic subcommand
17. The friend test (M1 gate)

The doc ends with **5 things I'm genuinely unsure about**, so
the user (or the next session) can challenge any of them
before work starts:

1. Is 17 the right number? Maybe M1.13 + M1.14 should be one.
2. Should the gate be a stricter automated test, not the friend test?
3. Is the `--log-level` flag necessary in M1 or just polish?
4. Is the QR code (M1.10) really M1 or M1.5?
5. Are there dependency-graph edges I missed?
